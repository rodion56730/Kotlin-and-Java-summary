## Kotlin: базовый синтаксис

### val / var / const val

```kotlin
val x = 5        // неизменяемая ССЫЛКА, значение можно узнать в runtime
var y = 5         // изменяемая ссылка

const val MAX = 100 // компайл-тайм константа: только top-level или companion object,
                     // только примитивы/String, значение известно ДО запуска
```

**Частая ошибка:** путать `val` и `const val`. `val` может быть проинициализирован в runtime (результатом функции), `const val` — только на этапе компиляции.

### == vs ===

```kotlin
data class Person(val name: String)
val p1 = Person("Tom")
val p2 = Person("Tom")

p1 == p2   // true  — структурное равенство (вызывает .equals())
p1 === p2  // false — разные объекты в памяти
p1 === p1  // true  — один и тот же объект
```

`==` смотрит внутрь объекта (содержимое), `===` смотрит на адрес в памяти.

### lateinit vs lazy

||`lateinit var`|`by lazy { }`|
|---|---|---|
|Тип|только `var`|только `val`|
|Кто инициализирует|ты сам, вручную, в любом месте|автоматически, при первом чтении|
|Примитивы|не поддерживает|поддерживает|
|Потокобезопасность|нет|да, по умолчанию|

```kotlin
lateinit var binding: ActivityMainBinding // назначаешь сам позже

val config: Config by lazy {               // вычислится 1 раз, при первом обращении
    loadConfigFromDisk()
}
```

### List vs MutableList, иммутабельность

```kotlin
val mutableList = mutableListOf(1, 2, 3)
val readOnlyView: List<Int> = mutableList   // это ТОТ ЖЕ объект, просто урезанный интерфейс
mutableList.add(4)
println(readOnlyView) // [1, 2, 3, 4] — тоже изменился!
```

`List` в Kotlin — **read-only view**, а не гарантированная иммутабельность.

**Зачем иммутабельность — хорошая практика:**

- потокобезопасность (не нужны локи для чтения)
- предсказуемость (объект не поменяется "из-под тебя")
- проще дебажить (изменение = новый объект через `copy()`)
- нужна для корректной работы recomposition в Compose

### data class — полный список того, что генерируется

`equals()`, `hashCode()`, `toString()`, `copy()`, `componentN()` (для деструктуризации). Геттер генерируется всегда, сеттер — только для `var`-полей.

## Coroutines

### suspend fun — механика

Нельзя вызвать suspend-функцию из обычной — это ошибка **компиляции**, а не рантайм-проблема:

```kotlin
suspend fun fetchData(): String { ... }

fun regular() {
    fetchData() // ❌ ошибка компиляции
}

fun regular() {
    viewModelScope.launch {
        fetchData() // ✅ ок, внутри корутины
    }
}
```

Suspend-функцию можно вызвать только из другой suspend-функции или из corutine builder (`launch`, `async`, `runBlocking`).

### CoroutineScope

- `viewModelScope` — живёт до `onCleared()` ViewModel
- `lifecycleScope` — живёт до `onDestroy()` Activity/Fragment
- `GlobalScope` — живёт всё время работы приложения, **не отменяется** при уничтожении экрана → анти-паттерн, риск утечек и бессмысленной работы в фоне

### Handler / Looper

Механизм, на котором построен `Dispatchers.Main` под капотом.

- **`Looper`** — крутит бесконечный цикл в потоке, достаёт задачи из очереди (`MessageQueue`) одну за другой. У главного потока `Looper` создаётся автоматически.
- **`Handler`** — отправляет задачи в очередь конкретного `Looper`а.

```kotlin
val mainHandler = Handler(Looper.getMainLooper())

Thread {
    val result = doHeavyNetworkCall() // фоновый поток
    mainHandler.post {
        textView.text = result // выполнится в главном потоке
    }
}.start()
```

## Архитектура

### LiveData vs StateFlow

||LiveData|StateFlow|
|---|---|---|
|Платформа|Android Jetpack|Kotlin Coroutines (можно и не в Android)|
|Lifecycle-awareness|встроена|нужно вручную (`repeatOnLifecycle`)|
|Поток для наблюдателей|главный|любой|
|Начальное значение|не обязательно|обязательно|

Сейчас в новых проектах рекомендуют **StateFlow** — часть более широкой экосистемы Flow.

### ViewModel lifecycle

`ViewModel` **не синглтон на всё приложение**. Она привязана к своему `ViewModelStoreOwner` и живёт, пока жив он:

- при повороте экрана — Activity пересоздаётся, но `ViewModelStore` передаётся дальше → ViewModel **не пересоздаётся**
- при `finish()`/полном закрытии Activity — `ViewModelStore` очищается, вызывается `onCleared()`

### Room: три официальных компонента

1. **`@Entity`** — описывает таблицу
2. **`@Dao`** — интерфейс с методами доступа к данным
3. **`@Database`** — объединяет Entity и DAO

**`Repository` — НЕ часть Room**, это архитектурный паттерн уровня приложения (обычно объединяет Room + сеть).

### Offline-first паттерн (single source of truth)

UI никогда не общается с сетью напрямую. UI подписан только на Room (через `Flow`), Repository в фоне обновляет Room из сети.

```kotlin
class NewsRepository(private val dao: NewsDao, private val api: NewsApi) {
    fun getNews(): Flow<List<News>> = dao.getAllNews() // единственный источник правды

    suspend fun refreshNews() {
        val fresh = api.fetchNews()
        dao.insertAll(fresh) // Flow из dao сам "проснётся" и отдаст новые данные
    }
}
```

### Dependency Injection

DI — принцип, при котором объект **получает зависимости извне** (через конструктор), а не создаёт их сам.

**Зачем:** тестируемость (можно подставить mock), слабая связанность, переиспользование.

Hilt/Dagger — конкретные **инструменты**, автоматизирующие DI на Android (не путать понятие DI с инструментом).

## RecyclerView

### ViewHolder — точное определение

Класс-обёртка, которая **хранит ссылки на View одной ячейки**, чтобы не вызывать `findViewById()` заново при каждой прокрутке. RecyclerView создаёт ограниченное число View и переиспользует их при скролле.

### DiffUtil

Сравнивает старый и новый список, вычисляет **минимальный набор операций** (Myers diff — тот же принцип, что в `git diff`), вызывает точечные `notifyItemInserted/Removed/Moved/Changed` вместо `notifyDataSetChanged()`.

```kotlin
class UserDiffCallback(private val old: List<User>, private val new: List<User>) : DiffUtil.Callback() {
    override fun areItemsTheSame(oldPos: Int, newPos: Int) = old[oldPos].id == new[newPos].id
    override fun areContentsTheSame(oldPos: Int, newPos: Int) = old[oldPos] == new[newPos]
}
```

На практике почти всегда используют готовый **`ListAdapter`** — уже включает DiffUtil, сравнение асинхронное.

**Стандартный ответ на "RecyclerView тормозит":** ViewHolder reuse + DiffUtil + кэширование картинок (Glide/Coil) + плоская иерархия layout.

## View-based Android

### ConstraintLayout — зачем

Позволяет строить **плоскую иерархию** вместо вложенных `LinearLayout`/`RelativeLayout`. Глубокая вложенность = больше measure/layout проходов = хуже производительность, особенно у `RelativeLayout`, который может измерять children несколько раз.

### wrap_content / match_parent / 0dp

- `wrap_content` — по размеру содержимого
- `match_parent` — на весь размер родителя
- **`0dp`** — НЕ "нет отступа"! Означает "вычисли размер по правилам, заданным отдельно":
    - в `LinearLayout` + `layout_weight` — раздели пространство пропорционально weight
    - в `ConstraintLayout` — "match constraint", растянись между указанными constraints

### Fragment back stack

По умолчанию транзакции **не** попадают в back stack — нужно явно:

```kotlin
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment())
    .addToBackStack("detail") // явно!
    .commit()
```

Без `addToBackStack()` — при нажатии "Назад" транзакция как будто не существовала, откат идёт к **последней транзакции, реально попавшей в стек** (а не обязательно к Activity — если до этого что-то добавлялось в стек, откатимся туда).

### Service

**Важно:** Service по умолчанию работает **в том же процессе и потоке**, что и остальное приложение — НЕ создаёт отдельный поток автоматически. Если внутри Service выполнить синхронную тяжёлую операцию — получишь ANR точно так же, как в Activity.

Смысл Service — не многопоточность, а **жизненный цикл, независимый от UI** (работает, даже когда все Activity закрыты). Для фоновых задач с гарантией выполнения сейчас рекомендуют **WorkManager**.

### BroadcastReceiver

Слушает системные/кастомные широковещательные сообщения (заряд батареи, изменение сети, GPS). С Android 8+ большинство implicit broadcast нельзя регистрировать статически в манифесте — только динамически, с обязательной отпиской в `onDestroy()`/`onPause()`.

### TextWatcher — валидация EditText в реальном времени

```kotlin
emailEditText.addTextChangedListener(object : TextWatcher {
    override fun beforeTextChanged(s: CharSequence?, start: Int, count: Int, after: Int) {}
    override fun onTextChanged(s: CharSequence?, start: Int, before: Int, count: Int) {}
    override fun afterTextChanged(s: Editable?) {
        val isValid = Patterns.EMAIL_ADDRESS.matcher(s.toString()).matches() // готовый regex от Android
        emailInputLayout.error = if (!isValid) "Некорректный email" else null
    }
})
```

Для живой валидации часто **дебаунсят** ввод (~300-500мс паузы), чтобы не показывать ошибку, пока пользователь ещё печатает.

### ViewBinding vs DataBinding

**ViewBinding** — типобезопасная замена `findViewById()`, генерирует класс `Binding` для каждого layout:

```kotlin
binding = ActivityMainBinding.inflate(layoutInflater)
setContentView(binding.root)
binding.nameText.text = "Hello" // типобезопасно, без findViewById
```

**DataBinding** — надмножество ViewBinding: можно биндить данные прямо в XML (`android:text="@{viewModel.name}"`), поддерживает two-way binding. Требует `<layout>`-обёртку, увеличивает время сборки. В большинстве современных проектов достаточно ViewBinding.

## Jetpack Compose

### State Hoisting

Composable-функция не хранит state сама, а получает его снаружи как параметр + сообщает об изменениях через колбэк:

```kotlin
// Stateless — переиспользуемый, тестируемый
@Composable
fun SearchField(text: String, onTextChange: (String) -> Unit) {
    TextField(value = text, onValueChange = onTextChange)
}
```

Правило: экран (`XxxScreen`) обычно stateful (читает ViewModel), мелкие переиспользуемые компоненты — stateless.

### Modifier — порядок важен

```kotlin
Modifier.padding(16.dp).background(Color.Red)  // отступ НЕ закрашен
Modifier.background(Color.Red).padding(16.dp)  // отступ ЗАКРАШЕН (фон применился раньше, на весь размер)
```

Каждый модификатор оборачивает результат предыдущих — как матрёшка, снаружи внутрь.

### key в LazyColumn

```kotlin
LazyColumn {
    items(transactions, key = { it.id }) { TransactionRow(it) }
}
```

Без `key` Compose идентифицирует элементы **по позиции**. При сортировке/перестановке это заставляет перерисовывать все элементы заново (теряется локальный state, ломаются анимации перемещения). С `key` Compose узнаёт "тот же" элемент на новой позиции и просто перемещает его. Прямой аналог `areItemsTheSame()` в DiffUtil.

### LaunchedEffect

Запускает suspend-код, привязанный к композиции:

```kotlin
LaunchedEffect(userId) { // key = userId
    viewModel.loadUser(userId)
}
```

- при первом входе в композицию — запускает блок
- если key не изменился — не перезапускается
- если key изменился — старая корутина отменяется, запускается новая с новым key
- `LaunchedEffect(Unit)` — выполнится ровно один раз

### DisposableEffect

Нужен, когда есть что явно очистить (listener, подписка не на корутину):

```kotlin
DisposableEffect(Unit) {
    val listener = SensorListener { ... }
    sensorManager.registerListener(listener)
    onDispose { sensorManager.unregisterListener(listener) }
}
```

### rememberCoroutineScope vs LaunchedEffect

||LaunchedEffect|rememberCoroutineScope|
|---|---|---|
|Когда запускается|автоматически, при входе в композицию/смене key|вручную, по требованию (`.launch{}`)|
|Сценарий|загрузка данных при открытии экрана|запуск действия по клику|
|Откуда вызывается|прямо в теле Composable|из non-suspend лямбды (onClick)|

```kotlin
val scope = rememberCoroutineScope()
Button(onClick = {
    scope.launch { snackbarHostState.showSnackbar("Сохранено!") }
})
```

### derivedStateOf

Нужен, когда state вычисляется из другого state, который меняется **гораздо чаще**, чем сам результат:

```kotlin
val showButton by remember {
    derivedStateOf { listState.firstVisibleItemIndex > 0 }
}
```

`firstVisibleItemIndex` меняется на каждый пиксель скролла — без `derivedStateOf` recomposition происходил бы на каждое изменение индекса, а не только когда `showButton` реально меняется с true на false.

### @Stable / @Immutable

Compose перед recomposition проверяет, изменились ли параметры. Если тип "нестабилен" (например, содержит `MutableList`), компилятор не может доверять сравнению и **пессимистично** пропускает оптимизацию.

```kotlin
@Immutable
data class UserUiState(val name: String, val favorites: List<String>)
```

`@Immutable` — обещание компилятору "объект никогда не изменится после создания". `@Stable` — более гибкий вариант для случаев, когда мутация есть, но Compose гарантированно об этом узнает.

### Производительность списков — Compose-специфика

Кроме общих причин (кэш картинок, `key`):

- **нестабильные лямбды**, пересоздающиеся на каждый recomposition (`onClick = { viewModel.onLike(post.id) }` без `remember`)
- тяжёлые вычисления в теле Composable без `remember`
- отсутствие `contentType` при разных типах карточек в одном списке

### CompositionLocal

Передача данных вниз по дереву Composable, минуя явные параметры на каждом уровне — для действительно кросс-cutting данных (тема, Context, локаль).

```kotlin
val context = LocalContext.current // без передачи параметром через 5 уровней

val LocalUserSession = compositionLocalOf<UserSession?> { null }
CompositionLocalProvider(LocalUserSession provides session) {
    ProfileScreen() // внутри доступно LocalUserSession.current
}
```

Не замена обычной передаче параметров — анти-паттерн, если используется просто "чтобы не прокидывать".

### Scaffold и Slot API

`Scaffold` — структурный skeleton экрана (Material Design), НЕ про тему всего приложения (это `MaterialTheme`).

```kotlin
Scaffold(
    topBar = { TopAppBar(title = { Text("Экран") }) },
    floatingActionButton = { FloatingActionButton(onClick = {}) { Icon(...) } }
) { innerPadding -> // важно применить эти отступы к контенту!
    LazyColumn(modifier = Modifier.padding(innerPadding)) { ... }
}
```

**Slot API** — паттерн, при котором компонент принимает другие Composable как параметры (лямбды), отвечая только за их расположение. Примеры: `Scaffold`, `Card { }`, `Button { }`.

### Collapsing TopBar при скролле

Готовый механизм, не нужно писать вручную:

```kotlin
val scrollBehavior = TopAppBarDefaults.exitUntilCollapsedScrollBehavior()
Scaffold(
    modifier = Modifier.nestedScroll(scrollBehavior.nestedScrollConnection),
    topBar = { TopAppBar(title = { Text("Профиль") }, scrollBehavior = scrollBehavior) }
) { ... }
```

### ConstraintLayout в Compose

Нужен, когда `Column`/`Row`/`Box` заставляют городить глубокую вложенность для сложного относительного позиционирования. На практике используется реже, чем в View-мире — Compose и так не так чувствителен к вложенности (single-pass measurement).

### Побочные эффекты в теле Composable

Тело `@Composable` функции может вызываться Compose runtime **непредсказуемое число раз** (пропущено, вызвано повторно) — поэтому побочные эффекты (аналитика, логи, сетевые вызовы) нельзя писать напрямую в теле, только через `LaunchedEffect`/`SideEffect`/`DisposableEffect`, которые дают предсказуемые гарантии выполнения.

### VisualTransformation

Форматирование ввода (пробелы в сумме, маска телефона) без "прыжков" курсора — реальное значение хранится "чистым", форматирование применяется только визуально:

```kotlin
TextField(
    value = rawValue,
    onValueChange = { rawValue = it.filter { c -> c.isDigit() } },
    visualTransformation = MoneyVisualTransformation()
)
```

`OffsetMapping` внутри `VisualTransformation` описывает соответствие позиций курсора между "сырым" и отформатированным текстом.

## Git

### merge vs rebase

```bash
git checkout feature/login
git fetch origin
git merge origin/main   # создаёт merge-коммит, сохраняет реальную историю
# или
git rebase origin/main  # переставляет твои коммиты поверх main, история линейная, переписывает хэши
```

- `merge` — безопасно, но история "грязнее"
- `rebase` — чище история, но переписывает коммиты (нельзя force-push в общую ветку, где работают другие)

"Update Project" в Android Studio по умолчанию делает pull для текущей ветки относительно её origin, а не относительно `main` — чтобы подтянуть `main`, нужно явно fetch + merge/rebase `origin/main`.

## Intent (справочно, было отдельным материалом)

- **Explicit** — указывает конкретный класс (`Intent(this, DetailActivity::class.java)`), для навигации внутри приложения
- **Implicit** — описывает действие (`ACTION_VIEW`, `ACTION_SEND`), систему сама находит обработчик, может выйти за пределы приложения
- Extras ограничены ~1 МБ (Binder-буфер) — большие объекты (Bitmap) передавать нельзя, только id/URI
- `PendingIntent` — обёртка Intent для выполнения от имени приложения в будущем (уведомления, AlarmManager), с Android 12+ обязателен `FLAG_IMMUTABLE`
- Современный способ получить результат — `ActivityResultLauncher`, а не устаревший `startActivityForResult`

## Приоритет повторения перед собесом

1. **Kotlin base** (val/const val, ==/===) — должно быть автоматическим
2. **State hoisting + key + Modifier порядок** в Compose — самое частое в продуктовой команде
3. **ViewHolder + DiffUtil** — стандартный ответ на вопрос про производительность списков
4. **ViewModel lifecycle** — переживает поворот, но не синглтон на всё приложение
5. Остальное — по возможности, не критично для стажировки
