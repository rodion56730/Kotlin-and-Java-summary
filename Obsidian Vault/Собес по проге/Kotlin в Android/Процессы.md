# Конспект: Процессы в Android

## Общая идея

Каждое Android-приложение по умолчанию запускается в своём **отдельном Linux-процессе** со своим экземпляром Dalvik/ART VM. Это даёт изоляцию (одно приложение не может напрямую читать память другого) и безопасность (каждому процессу назначается свой Linux UID).

- Один APK/приложение = как правило один процесс, но можно явно указать в `AndroidManifest.xml`, что отдельный компонент (`Activity`, `Service`) должен работать в **отдельном процессе**:

```xml
<service
    android:name=".MyService"
    android:process=":background" />
```

```
- `:background` — приватный процесс внутри приложения (с двоеточием)
- `com.example.remote` — глобальный именованный процесс, к которому могут подключаться другие приложения (без двоеточия)
```

## Кто управляет процессами

Процессами управляет **Activity Manager** (часть System Server), а не разработчик напрямую. Разработчик не может "закрыть" процесс приложения гарантированно — Android сам решает, когда завершить процесс, исходя из приоритета и нехватки памяти (**Low Memory Killer** / **LMKD**).

## Приоритеты процессов (от высшего к низшему)

Система классифицирует процессы по важности, чтобы решать, какой процесс убить первым при нехватке памяти:

1. **Foreground process** — highest priority
    
    - Пользователь напрямую взаимодействует с Activity (`onResume`)
    - Есть привязанный `Service`, который вызвал `startForeground()`
    - Выполняется `BroadcastReceiver.onReceive()`
    - Почти никогда не убивается системой (только в крайнем случае)
2. **Visible process**
    
    - Activity видна пользователю, но не в фокусе (`onPause`, например частично перекрыта диалогом)
    - Есть `Service`, привязанный к видимой Activity
3. **Service process**
    
    - Работает обычный (не foreground) `Service`, например синхронизация данных в фоне
4. **Cached / Background process**
    
    - Activity не видна (`onStop`), не содержит активных компонентов
    - Хранится системой "про запас" для быстрого возврата пользователя (LRU-список)
    - Убивается первым при нехватке памяти
5. **Empty process**
    
    - Процесс без активных компонентов, оставлен только ради кэширования для более быстрого следующего запуска

> На собеседовании часто спрашивают именно порядок приоритетов и как избежать того, чтобы систему "убила" ваш процесс во время важной операции.

## Process Death и восстановление состояния

Ключевая для Android тема: система может **убить процесс приложения в фоне** в любой момент (не путать с завершением Activity пользователем через "Назад").

- При этом Activity стек **запоминается системой**, а не приложением — при возврате пользователя процесс поднимается заново.
- Чтобы восстановить UI-состояние, Android вызывает `onSaveInstanceState(Bundle)` перед уничтожением и передаёт этот `Bundle` обратно в `onCreate(savedInstanceState)` при пересоздании.
- Начиная с Jetpack, для ViewModel есть **`SavedStateHandle`** — переживает process death (в отличие от простого поля в `ViewModel`, которое переживает только configuration change, но не process death).

| Событие                                   | ViewModel (обычный) | `SavedStateHandle`      | `onSaveInstanceState` |
| ----------------------------------------- | ------------------- | ----------------------- | --------------------- |
| Поворот экрана (config change)            | ✅ сохраняется       | ✅ сохраняется           | ✅ сохраняется         |
| System-initiated process death            | ❌ теряется          | ✅ сохраняется           | ✅ сохраняется         |
| Явное закрытие пользователем (swipe/Back) | ❌ теряется          | ❌ теряется (по дизайну) | ❌ теряется            |

## Multiprocess (несколько процессов в одном приложении)

Зачем разносить компоненты по процессам:

- Изоляция тяжёлых/нестабильных частей (например, WebView, плагины) — крэш одного процесса не убивает всё приложение
- Экономия памяти основного процесса (например, вынести аналитику/фоновую синхронизацию в отдельный процесс)

Минусы:

- Каждый процесс = отдельный экземпляр `Application` класса и статических полей — **нельзя просто делиться синглтонами/памятью между процессами**
- Нужен IPC (Inter-Process Communication): `Binder`, `AIDL`, `ContentProvider`, `Intent`+`BroadcastReceiver`
- Дороже по памяти (каждый процесс = отдельная ART VM)

## IPC — как процессы общаются между собой

- **Binder** — основной механизм IPC в Android, лежит в основе `bindService()`, `AIDL`, системных сервисов
- **AIDL (Android Interface Definition Language)** — генерирует Binder-интерфейсы для сложного межпроцессного взаимодействия
- **ContentProvider** — стандартный способ шарить структурированные данные между приложениями/процессами
- **Intent + BroadcastReceiver** — простой способ передать событие/данные между процессами

## Application класс и процесс

- `Application.onCreate()` вызывается **один раз на процесс**, до создания любых Activity/Service в этом процессе.
- Если у приложения несколько процессов (multiprocess), `Application.onCreate()` выполнится в **каждом** из них отдельно — важно учитывать при инициализации SDK (например, не инициализировать тяжёлые SDK в дочерних процессах, проверяя имя процесса через `ActivityManager` или `Application.getProcessName()`).

## OOM (Out Of Memory) и Low Memory Killer

- Android использует адаптацию Linux `oom_adj`/`oom_score` — у процесса выставляется числовой приоритет, и при нехватке памяти система убивает процессы с наименьшим приоритетом (наибольший `oom_adj`).
- `onTrimMemory(level)` — колбэк, который получает приложение, когда системе не хватает памяти, с разными уровнями (`TRIM_MEMORY_RUNNING_LOW`, `TRIM_MEMORY_UI_HIDDEN`, `TRIM_MEMORY_COMPLETE` и т.д.) — стоит освобождать кэши по этому сигналу.
- Устаревший `onLowMemory()` — более грубый аналог, срабатывает при критической нехватке памяти.
